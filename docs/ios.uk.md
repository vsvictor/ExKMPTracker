# Інтеграція з iOS

`IosTrackerRuntime` — це нативний адаптер життєвого циклу спільного трекера. Він керує
CoreLocation/CoreMotion, запускає найкращий доступний таймер `Tick` з інтервалом одна секунда
та використовує захищені сховища черги й сесії. Runtime належить окремому екземпляру:
створюйте його з `CoroutineScope`, яким керує застосунок, і власним автентифікованим
`TrackingTransport`; не використовуйте глобальний singleton. Застосунок має створити
`TrackingSession` лише після підтвердження зміни користувачем і сам вирішувати, коли відновити
збережену сесію.

## Збірка та підключення

На macOS із Xcode та встановленим Kotlin/Native toolchain виконайте:

```sh
./gradlew :tracker:assembleExKMPTrackerXCFramework
```

Додайте отриманий `ExKMPTracker.xcframework` до target застосунку в Xcode або поширюйте його як
бінарний framework. Якщо Xcode не додає системні залежності автоматично, підключіть Apple
frameworks `CoreLocation`, `CoreMotion`, `Foundation` і `Security`. Framework статичний та
налаштований для `iosArm64` і `iosSimulatorArm64`.

Реалізуйте `TrackingRpcClient` поверх наявного автентифікованого RPC-з'єднання хоста.
Новий HTTP-клієнт чи з'єднання не створюються. Дивіться [контракт CoopNav](coopnav.uk.md):

```swift
let transport = HostRpcTrackingTransport(client: hostRpcClient)
let runtime = IosTrackerRuntime(transport: transport)

let identity = try TrackingIdentity(driverId: driverID, brandId: brandID)
let session = try TrackingSession(sessionId: confirmedSessionID, identity: identity)
// Лише після того, як Info.plist містить UIBackgroundModes=location і обидва описи доступу
// до геолокації, а сам застосунок отримав дозвіл Always (і Precise):
try await runtime.startConfirmedSession(
    session: session,
    backgroundLocationConfigured: true
)

let stateObservation = runtime.observeState { snapshot in
    render(snapshot)
}
```

`IosTrackerRuntime(transport:)` — точний ініціалізатор з одним аргументом (аргументи Kotlin за
замовчуванням у Swift не експортуються). Явна Swift-альтернатива —
`IosTrackerRuntime(transport:config:logger:storage:)`. Обидва володіють власним coroutine scope.
`startConfirmedSession(session:)` без прапорця працює лише на передньому плані.

Запуск, відновлення, зупинка та завершення серіалізуються в межах екземпляра runtime. Виклик
`startConfirmedSession` під час роботи з тією самою ідентичністю водія/бренду оновлює
збережену сесію та сесію BLoC без перезапуску CoreLocation/CoreMotion (змінений фоновий
прапорець застосовується до вже запущеного location manager). Інша ідентичність спочатку
повністю зупиняє стару сесію, зокрема очищає її збережену копію, і лише потім запускає нову;
якщо зупинка не вдалася, помилка передається у Swift, а нова сесія не запускається.

`restoreSavedSession(backgroundLocationConfigured:)` викликається лише явно: створення runtime саме по собі не відновлює
сесію. `stop()` завершує сесію та видаляє збережену ідентичність, але не видаляє поставлені в
чергу точки маршруту. Зупинка виконується безумовно: таймер, callbacks CoreLocation і
CoreMotion та сесія BLoC зупиняються в гарантованому cleanup, навіть якщо окремий крок
завершився помилкою. Якщо очистити збережену сесію не вдалося, відстеження все одно
зупиняється, помилка логується і відображається в `TrackerState.error`, після чого `stop()`
передає її у Swift як помилку. Перед видаленням файлу сесії `stop()` надійно записує маркер
зупинки; поки він існує, `restoreSavedSession()` повертає `nil`, тож зупинену сесію не буде
відновлено під час наступного запуску. Маркер замінює лише новий `startConfirmedSession`.
`shutdown()` зупиняє нативні ресурси й BLoC, але залишає збережену
сесію для подальшого явного відновлення; переданий `CoroutineScope` і далі належить
застосунку. Не викликайте `shutdown()` лише через перехід застосунку у фон.
`StateFlow<TrackerState>` BLoC доступний безпосередньо як `runtime.state`; метод
`observeState` надає Swift-friendly callback для того самого потоку та повертає
`IosStateObservation` з методом `cancel()` без параметрів. Власник кожного handle має явно
його скасувати. Скасуйте спостерігача та зупиніть/завершіть runtime:

```swift
stateObservation.cancel()
try await runtime.stop()       // пропустіть, якщо збережену сесію буде явно відновлено пізніше
try await runtime.shutdown()
```

Swift-ініціалізатори створюють власний coroutine scope і скасовують його під час
`shutdown()`. Kotlin-застосунок може передати власний scope через основний конструктор; він
залишається під керуванням застосунку, а `shutdown()` скасовує й очікує лише внутрішнього
спостерігача опорного курсу, тож довгоживучий scope застосунку не утримує runtime. Runtime не закриває довільний переданий transport.
Swift callback спостереження повертає `Void`.

`HostRpcTrackingTransport` адаптує callbacks JSON-результатів наявного клієнта та
передає скасування через `TrackingRpcCall.cancel()`. Хост додає поточний PASETO-токен у
параметри RPC та керує його оновленням і життєвим циклом з'єднання. Попередній
`IosJsonRpcTrackingTransport` доступний лише в необов'язковому модулі `:tracker-http`.
Kotlin suspend API з `@Throws` експортуються як throwing
Swift async/completion-handler API; використовуйте `try await` (або сигнатуру completion
handler зі згенерованого header) для `startConfirmedSession`, `restoreSavedSession`, `stop` і
`shutdown`. Точні сигнатури дивіться у згенерованому `ExKMPTracker.h`.

## Дозволи та налаштування застосунку

Бібліотека не запитує дозволи автоматично. Застосунок має пояснити функцію та запросити
дозволи у власному користувацькому сценарії. Додайте локалізовані описи призначення; перекладіть
значення для кожної підтримуваної мови застосунку:

```xml
<key>NSLocationWhenInUseUsageDescription</key>
<string>Місцезнаходження використовується для запису підтвердженої поїздки.</string>
<key>NSLocationAlwaysAndWhenInUseUsageDescription</key>
<string>Місцезнаходження використовується для запису підтвердженої поїздки у фоновому режимі.</string>
<key>NSMotionUsageDescription</key>
<string>Дані про рух і кроки допомагають покращити оцінки поїздки.</string>
```

Для безперервного визначення місцезнаходження у фоні додайте режим `location` у background
modes target застосунку (еквівалентний запис Info.plist):

```xml
<key>UIBackgroundModes</key>
<array>
    <string>location</string>
</array>
```

Передавайте `backgroundLocationConfigured = true` лише за наявності цього режиму та опису
Always Location у Info.plist. Runtime перевіряє обидва записи й вмикає
`allowsBackgroundLocationUpdates` лише коли CoreLocation також підтверджує дозвіл Always.
З дозволом When In Use відстеження працює лише на передньому плані. Застосунок окремо керує
запитом дозволів і Precise Location у власному UI/налаштуваннях: бібліотека не може підвищити
зменшену точність, а сирі GNSS-дані недоступні навіть із Precise. Runtime не викликає API
запиту дозволу.

Менеджер запитує найвищу навігаційну точність, нульовий фільтр відстані, тип активності
автомобільна навігація та вимикає автоматичну паузу. Це запити, а не гарантії: iOS може
обмежити частоту або призупинити виконання. Таймер з інтервалом одна секунда працює лише за
сприятливих умов і не гарантується під час призупинення процесу; за наявності дозволеного
фонового режиму оновлення місцезнаходження все ще можуть надходити через CoreLocation.
Немає гарантії точного 1 Hz, повторного запуску після примусового закриття чи відновлення після
нього. Застосунок має явно викликати `restoreSavedSession()` відповідно до власної політики.

## Нативні дані та обмеження

- Коректні свіжі значення `CLLocation` перетворюються на `LocationFix`. Відхиляються зразки,
  старші за 30 секунд, більш ніж на п'ять секунд у майбутньому, з некоректними координатами
  або точністю. Монотонний час зразка — поточний час `TrackerClock` мінус вік зразка, виміряний через `NSDate`.
- Джерело `gps` призначається, коли горизонтальна точність відповідає `maxGnssAccuracyMeters`
  і iOS повідомляє Full Accuracy. До iOS 14 цього прапорця немає, тож точний зразок
  позначається як `gps`. Інакше джерело — `fused`. Ця мітка не гарантує точності:
  Core Location і з Full Accuracy може дати радіус 50–65 м, а окремого network-провайдера
  на iOS немає. Такий зразок грубий. 10 секунд після фікса ≤ 25 м він ігнорується і ще
  60 секунд не може переініціалізувати фільтр. Швидкість/курс і точність цих
  значень передаються лише тоді, коли CoreLocation позначає їх валідними.
  Коло на мапі — це радіус фільтра, а не `horizontalAccuracy` цього зразка.
- `isSimulatedBySoftware` перевіряється на iOS 15 і новіших. Старіші версії консервативно
  повертають `false`, бо платформа не надає цього сигналу; `false` не доводить справжність
  зразка.
- CoreMotion запитує активні device-motion оновлення з частотою 50 Гц; фактична доставка залежить від ОС.
  Акселерометрія не містить гравітації та перетворюється з g у
  м/с². Адаптер надає перевагу вертикальній системі attitude з істинною північчю, а за її
  недоступності використовує магнітну північ, якщо вона підтримується. Прискорення й кутова
  швидкість обертаються у світову систему координат, а горизонтальне прискорення проєктується
  на прийнятий опорний курс; довільно орієнтована вісь телефона не вважається напрямком автомобіля.
  Для магнітної системи adapter чекає корекцію true/magnetic від CoreLocation перед передачею
  поздовжніх зразків. Кутова швидкість рискання — це від'ємна правобічна кутова швидкість
  навколо world-up, відповідно до курсу за годинниковою стрілкою від півночі. Якщо немає
  калібрування курсу/півночі, `longitudinalAcceleration` дорівнює `null` (з одноразовою
  діагностикою) замість вгаданого значення; справжній модуль лінійного прискорення та кутова
  швидкість рискання навколо world-up (потребує лише вертикального attitude і гіроскопа) все
  одно передаються, тож ядро може виявити спокій/стоянку під час холодного старту. Опорний курс береться лише з прийнятої оцінки BLoC `state.estimate`
  (через спостерігача стану runtime), а не з необроблених callbacks CoreLocation, тому mock,
  застарілі, неточні чи відхилені фікси не можуть калібрувати систему руху. Якорем є оцінка
  `gps`/`fused` у русі (≥1 м/с) з валідним курсом та збереженим часом прийнятого
  спостереження; оцінки dead reckoning можуть задавати поточний курс лише протягом 3 с після
  якоря. Без свіжого якоря лише поздовжнє прискорення стає `null`, а діагностика повідомляється.
  Класифікація активності та крокомір доступні лише коли працює відповідний
  сервіс CoreMotion.
- `compassDegrees` містить перевірений `CLHeading` від того ж `CLLocationManager`:
  `trueHeading` або `magneticHeading` плюс останню отриману CoreLocation різницю true/magnetic,
  якщо `trueHeading` ще не валідний. Курси з від'ємною або >45° точністю, старші за 1 с або
  не спостережені в межах 1 с від часу зразка руху пропускаються (`null`); курс ніколи не
  вигадується. Саме це робить прогноз кроків при ходьбі в ядрі придатним; без компаса він
  відхиляється. `CLHeading` — це напрямок верхнього краю пристрою, тому зсув компаса в ядрі
  й надалі застосовується.
- `pressureHpa` надходить від `CMAltimeter`, якщо барометр доступний (кПа × 10 = гПа). Кожне
  свіже вимірювання (≤1 с, з урахуванням відновлення) додається один раз до наступного зразка
  руху в межах 1 с, тож барометричне вето зупинки в ядрі бачить реальні зміни, а не повтори.
  Без барометра поле лишається `null`, а `PlatformError` повідомляється один раз.
- Коли BLoC позначає пристрій нерухомим і зупиняє безперервні device-motion та крокомір,
  акселерометр пробудження низької частоти (2 Гц) залишається активним, а розпізнавання
  активності й барометр продовжують працювати, тож справжні переходи до ходьби чи автомобіля
  відновлюють сенсори. Кожен зразок пробудження передається як `MotionSample` з модулем
  `‖a − g_ref‖` у м/с², де `g_ref` — *вектор* гравітації в системі пристрою, збережений з
  останнього зразка device-motion (≤5 с; інакше перший зразок пробудження з діагностикою).
  `g_ref` уточнюється лише підтверджено спокійними зразками (<0,2 м/с²), тож не підлаштовується
  під реальне тривале прискорення. Горизонтальний старт 2 м/с² дає ≈2 м/с² (лише норма
  `|‖a‖ − g|` дала б ≈0,2 м/с²). Навігаційні керування дорівнюють `null` (ніколи не вигадані нулі). Спільне ядро рахує три послідовні зразки понад 0,8 м/с² і
  викликає `setStationary(false)`, що перезапускає безперервний CoreMotion; ходьба чи керування
  автомобілем при цьому не стверджуються.
- Свідома відмінність iOS від Android: стан STILL **не** зупиняє Core Location. Оновлення
  акселерометра/активності CoreMotion самі по собі не гарантують пробудження чи відновлення
  призупиненого iOS-застосунку, тому вимкнення геолокації під час стоянки могло б завершити
  фонове відстеження. Безперервні оновлення геолокації (`pausesLocationUpdatesAutomatically =
  false`) працюють протягом усієї підтвердженої сесії; зменшуються лише безперервні device-motion і
  крокомір до низькочастотного акселерометра пробудження (активність і барометр працюють), а BLoC
  і далі приймає фікси. Опублікована позиція лишається на якорі зупинки, доки швидкість або зсув
  не знімуть утримання. Це надає перевагу точності та фоновій безперервності над економією
  батареї. Перевірка трьох зразків акселерометра гарантована лише поки процес виконується; вона
  не пробуджує застосунок після призупинення ОС. Моніторинг significant-change може лише
  допомогти грубому відновленню та не замінює цю перевірку.
  Доступність сенсорів/симулятора та дозволи можуть відрізнятися; недоступні сенсори
  відображаються в `sensorCapabilities` і повідомляються як `PlatformError`.
- iOS не надає даних сирого годинника GNSS-приймача або AGC. Runtime не створює фальшивих
  `Gnss` доказів. Також iOS не надає загальний мережевий трафік UID застосунку;
  `IosTrafficCounter` кидає `UnsupportedOperationException`, а не повертає вигадані нулі.
- Монотонний час `TrackerClock` — Darwin `clock_gettime(CLOCK_MONOTONIC_RAW)`: він іде далі під
  час сну пристрою та не залежить від змін настінного годинника, тому прогнози на 15 с і опорні
  дані на 300 с протерміновуються під час призупинення. Настінний час береться з `NSDate`. Час
  CoreMotion не враховує сон; його вік відносно `NSProcessInfo.systemUptime` перетворюється в
  монотонний домен, зразки старші за одну секунду відкидаються, а після виявленого сну зразки
  відкидаються до надходження свіжих часових міток руху. Вік `CLLocation`, виміряний через
  `NSDate`, може бути спотворений зміною настінного годинника протягом короткого життя зразка;
  застарілі зразки та зразки з майбутнього відхиляються.


## Збереження

Сховище передається через DI: екземпляр `IosProtectedStorage(directory:)` (за замовчуванням
`Application Support/com.exkmptracker`) має власний mutex, а `IosTrackQueue(storage:)` і
`IosSessionStore(storage:)` отримують його як залежність. Кожна публічна операція черги/сесії —
одна транзакція під цим mutex; блокування не вкладаються (спершу lifecycle-блокування runtime,
потім блокування сховища, ніколи навпаки). Глобального singleton сховища немає. Створюйте рівно
один екземпляр сховища на каталог у процесі та передавайте його всім чергам/сховищам сесії та
runtime, які використовують цей каталог; незалежні екземпляри на одному каталозі не
координуються й можуть перезаписати snapshot одне одного. Параметри runtime за замовчуванням
створюють один екземпляр, спільний для його черги та сховища сесії, тож двом runtime в одному
процесі слід передати спільне сховище (або різні каталоги).

`IosTrackQueue` тепер зберігає FIFO-рядки в базі SQLCipher із випадковим ключем
у Keychain (`AfterFirstUnlockThisDeviceOnly`), повними синхронними commit і
транзакційним підтвердженням точного префікса. Попередні захищені JSON snapshots
мігрують окремо для кожної ідентичності; атомарний маркер міграції запобігає
повторному імпорту після аварії. Пошкодження чи втрата ключа спричиняють явну
помилку без видалення даних. Нативне компонування, стабільні ідентифікатори
ключів, міграція й резервні копії описані у [сховищі](storage.uk.md).

`IosSessionStore` зберігає підтверджену сесію в тому самому захищеному сховищі ОС, а не в
Keychain (задокументоване й прийняте відхилення від сховища на основі Keychain). Дані захищені після першого розблокування пристрою та недоступні до нього.
Відновлення сесії залишається явним. Ідентифікатор сесії зберігається в цьому захищеному
сховищі; додатковий bearer token не зберігається. Власна реалізація `TrackingTransport`
відповідає за захист власних облікових даних автентифікації.
