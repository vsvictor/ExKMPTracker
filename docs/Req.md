
ТЕХНІЧНЕ ЗАВДАННЯ

Назва проєкту: CoopNav — Система високоточного та кооперативного геопозиціювання транспортних засобів
Архітектурний підхід: Модульна клієнт-серверна система на базі екосистеми vsvictor/JSON-RPC-2

1. Мета та призначення системи

Забезпечення безперервного, точного та захищеного від підміни (спуфінгу/РЕБ) визначення місцеположення автомобіля в реальному часі за рахунок трирівневої архітектури:
1. Точне автономне позиціювання (Single-Vehicle EKF): комбінування GNSS, інерціальних сенсорів (IMU), барометра та алгоритмів придушення дрейфу.
2. Кооперативне позиціювання (V2V / V2I2V): використання сусідніх автомобілів та міського транспорту як динамічних опорних маяків за допомогою комп'ютерного зору та низькозатримкового обміну даними.
3. Гібридний відеострімінг (Server-Offload CV): динамічне перенесення обчислень комп'ютерного зору на сервер для бюджетних пристроїв через протокол Media over QUIC (moq.dev).

2. Загальна архітектура та технологічний стек


2.1. Серверна частина (Backend — Rust Plugin)

• Базовий фреймворк: плагін json-rpc-2-coopnav, побудований за стандартом розширень vsvictor/JSON-RPC-2-OAuth2.
• Життєвий цикл: реалізує трейт ServerPlugin та підключається до BackendBuilder (json-rpc-2-backend) із зафіксованою ревізією ядра JSON-RPC-2 та патчами [patch.crates-io] для h3 / h3-quinn.
• Авторизація та безпека: інтеграція з AuthPlugin (json-rpc-2-oauth2) для валідації PASETO v4.local токенів та RBAC-прав через макрос #[authorize(scopes = "...")].
• Транспортний рівень (MultiTransportServer):
• QUIC (quic): основний мультиплексований транспорт для надійної передачі пакетів трекінгу (tracking.ingest), синхронізації часу (serverTime) та ініціалізації медіасесій.
• RUDP (rudp): високочастотний датаграмний канал без блокування черги (out-of-order, max_packet_size = 1200 байт) для обміну кооперативною телеметрією (coop.sync_peers).
• HTTP/1.1 (http1): експорт метрик Prometheus (/metrics), JSON-знімків (/metrics.json) та перевірки стану (/healthz) через RunningServer::health_handle.
• Сховище та гео-індекс (CoopNavStorage):
• RedisCoopNavStorage: ідемпотентна дедуплікація точок за 16-байтним hex id (SET NX EX), буферизація треків у Redis Streams (XADD) та просторовий індекс активних авто в реальному часі (GEOADD / GEOSEARCH у радіусі 200 м).
• InMemoryCoopNavStorage: резервна реалізація в пам'яті на базі DashMap для локальної розробки та тестів.
• Медіа-контур (Етап 3): ретранслятор moq-relay та фоновий воркер на базі Rust-крейтів moq-net, moq-tokio, hang, moq-json, jsonwebtoken.

2.2. Клієнтська частина (Незалежний модуль Kotlin Multiplatform)

• Архітектурна ізоляція: модуль coopnav-tracking-kmp розробляється як окрема незалежна бібліотека (для Android та iOS). Він не створює власних мережевих підключень, а підключається до основного клієнтського додатку (де працює vsvictor/JSON-RPC-2-Client-KMP) через абстрактний інтерфейс TrackingRpcTransport (call / notify).
• Розподіл коду:
• commonMain: розширений фільтр Калмана (TrackingFilter), алгоритми валідації та придушення дрейфу, тротлінг (TrackThrottle), інтерфейс зашифрованої черги (TrackQueueStorage), контролер адаптивного CV (AdaptiveCvController) та оркестратор CoopNavTracker.
• androidMain / iosMain: нативні провайдери сенсорів (PlatformSensorProvider), реалізація зашифрованої бази даних (SQLCipher), локальний інференс нейромереж та апаратне кодування відео.

3. Поетапний план реалізації та функціональні вимоги


ЕТАП 1: Точне автономне геопозиціювання (Single-Vehicle EKF)

Реалізація конвеєра трекінгу згідно зі специфікацією tracking.uk.md.
1. Збір сенсорних даних (PlatformSensorProvider):
   • fused (1 Гц): основне позиціювання (FusedLocationProviderClient / CLLocationManager).
   • gps (пасивний сирий слухач): координати, доплерівська швидкість/курс із заявленими точностями, ознака isMock, супутниковий час utcTimeMs, а також метрики радіоефіру AGC та C/N0 (GnssMeasurementsEvent.Callback на Android).
   • network (fallback): використовується лише за відсутності свіжих GNSS/fused фіксів > 10 с.
   • IMU (50 Гц) та Барометр: гравітаційно-компенсоване поздовжнє прискорення, кутова швидкість гіроскопа (з динамічним EMA-калібруванням bias 0.98/0.02) та швидкість зміни тиску dP/dt.
   • Активність та крокомір: стани STILL, WALKING, IN_VEHICLE та апаратний лічильник кроків.
2. Попередня валідація та захист від підміни (Anti-Spoofing):
   • Вік фікса в межах (−2 с, +10 с], сувора монотонність часу.
   • Пороги точності (68% радіус): GNSS/fused ≤ 20 м, network ≤ 50 м.
   • Anti-fake: відхилення isMock, швидкості > 220 км/год та «телепортації» після розривів > 15 с: (відстань − accuracy − 100 м) / Δt ≤ 220 км/год.
   • Детекція РЕБ: при ΔAGC < −6 дБ та |ΔC/N0| > 10 дБ-Гц точки маркуються прапорцями SUSPECTED_INTERFERENCE / SUSPECTED_SPOOFING.
   • Звірка часу (serverTime): оновлення еталона кожні 60 с (дійсний 300 с). Якщо GNSS-час розходиться з еталоном понад 2000 мс + RTT/2 + gnssUncertainty — фікс відхиляється.
3. Математичне ядро EKF (TrackingFilter у commonMain):
   • Вектор стану в локальній дотичній площині (сферична Земля R = 6 371 000 м): x = [E, N, v, ψ].
   • Конверсія точності через 2D-ґаусіан (χ²₂(0.68) = 2.27886856637673).
   • Інтегрування моделі «unicycle» кроками ≤ 0.1 с з процесним шумом Q = diag(1 м², 1 м², 1 (м/с)², 0.02 рад²).
   • Тест викидів Махаланобіса: d² = Δᵀ S⁻¹ Δ ≤ 13.8155 (χ²₂ на рівні 99.9%).
   • Оновлення стану та коваріації строго у формі Джозефа.
   • Вихідна точність за найбільшим власним значенням 2×2 коваріації: accuracy = √(2.27886856637673 · λ_max).
4. Прогнози (Dead Reckoning) та 5 механізмів придушення дрейфу:
   • Горизонт прогнозу до 15 с або до досягнення accuracy > 100 м.
   • ZUPT: фіксація нульової швидкості після 10 тихих зразків IMU (< 0.2 м/с²) за умови барометричного вето (|dP/dt| < 0.02 гПа/с).
   • Кламп малих швидкостей: обнулення швидкості при v < 0.3 м/с та |a| < 0.3 м/с².
   • Неголономне обмеження (NHC): поперечний процесний шум знижується до 0.1 м²/с у режимі IN_VEHICLE.
   • Утримання точки зупинки: гістерезис входу/виходу (< 0.5 м/с / > 1.5 м/с) та одноразове уточнення якоря зваженим середнім.
5. Тротлінг та зашифрована FIFO-черга:
   • Запис точки при зміні дистанції ≥ 25 м, зміні курсу ≥ 10° (при v > 1 м/с) або інтервалі ≥ 30 с.
   • Фіксація стану тротлінгу (commitRecorded) відбувається виключно після успішного запису в базу даних.
   • Ізоляція черги за ключем (brandId, driverId).
   • Відправка пакетів по ≤ 100 точок кожні ≥ 10 с через tracking.ingest та видалення лише підтвердженого FIFO-префікса acceptedIds.

ЕТАП 2: Кооперативне позиціювання (Cooperative Positioning / V2V)

Використання сусідніх машин як опорних навігаційних маяків при деградації або підміні власного GNSS.
1. Візуальна детекція сусідів (Edge CV на клієнті):
   • Інтеграція легкої нейромережі YOLOv8n / YOLOv11n (CoreML на iOS, LiteRT/TFLite з NPU/GPU делегатом на Android) із частотою 15–30 FPS.
   • Визначення класу ТЗ (car, truck, bus, trolleybus), дистанції \(d\) (м), азимутального кута \(\theta \) (град) та відносної швидкості \(\Delta v\).
2. Серверний Matching Engine (RedisCoopNavStorage):
   • Метод coop.sync_peers (10 Гц по RUDP/QUIC): приймає поточний стан EKF клієнта, trust_score та список спостережуваних об'єктів observed_peers.
   • Пошук активних сусідів у радіусі 200 м через GEOSEARCH + пакетне читання станів (MGET), фільтрація за trust_score >= 0.7 (відсіювання машин під РЕБ).
   • Лінійна екстраполяція координат сусідів на мітку часу запиту клієнта (компенсація мережевого RTT).
   • Зіставлення візуальних векторів камери з екстрапольованими координатами сусідів у межах допуску 12 м та повернення підтверджених «донорів».
   • Інтеграція громадського транспорту (GTFS-Realtime): фоновий воркер плагіна підтягує відкриті GPS-потоки міських автобусів і тролейбусів у гео-індекс як стабільні опорні маяки для вирішення проблеми «холодного старту».
3. Кооперативне оновлення EKF (cooperativeFix у TrackingFilter):
   • Обчислення псевдовиміру власної позиції від координат донора та вектора камери \((d, \theta)\).
   • Врахування сумарної дисперсії (\(\sigma^2_{donor} + \sigma^2_{vision}\)), проходження тесту викидів Махаланобіса та оновлення стану у формі Джозефа.

ЕТАП 3: Гібридний відеострімінг та Server-Offload CV (Media over QUIC)

Забезпечення кооперативного режиму на бюджетних смартфонах без перегріву та втрати автономності.
1. Адаптивний контролер режимів (AdaptiveCvController у commonMain):
   • Моніторинг локального FPS інференсу YOLO та термального стану пристрою.
   • При падінні продуктивності нижче 10 FPS протягом 5 секунд — вимкнення локальної нейромережі (EDGE_CV) та перехід у режим трансляції відео (OFFLOAD_CV).
2. Авторизація та ініціалізація потоку (coop.request_moq_ingest):
   • Клієнт запитує дозвіл на стрімінг через JSON-RPC-2-Client-KMP.
   • Серверний плагін генерує підписаний JWT-токен (через jsonwebtoken / moq-auth) та повертає адресу ретранслятора moq-relay, шлях публікації coopnav/v1/{sessionId} і максимальний час життя групи кадрів max_group_age_ms = 80 мс.
3. Публікація синхронізованих медіатреків (moq.dev Rust crates):
   • Клієнт через moq-ffi та moq-video (апаратне кодування H.264/H.265 640×360 @ 15 FPS без B-frames) публікує два синхронізовані треки в межах одного broadcast-потоку:
   • video.hang — відеокадри (із механізмом Adaptive Latency та On-Demand доставкою — кодування стартує лише за наявності активного підписника);
   • imu.json (moq-json) — потокові дельти орієнтації камери (pitch, roll, yaw, capture_timestamp_ms).
4. Серверний CV Offload Worker (MoqCvOffloadWorker на Rust):
   • Підписується на анонсовані потоки coopnav/v1/* через moq-net / moq-tokio.
   • Декодує кадри на GPU (NVDEC), виконує детекцію сусідів, прив'язує їх до кутів з треку imu.json та передає вектори (d, θ) напряму в RedisCoopNavStorage.
   • Відеокадри існують виключно в RAM/VRAM серверного воркера і негайно знищуються після інференсу без запису на диск.

4. Специфікація JSON-RPC 2.0 методів плагіна

Усі методи реєструються в RpcServer із JSON Schema через RpcServer::document_method(...) для підтримки автоматичного виявлення (rpc.list_methods):

Метод	Транспорт	Етап	Призначення
serverTime	QUIC	Етап 1	Повертає { "serverTimeMs": u64 } для розрахунку зсуву та невизначеності годинника пристрою.
tracking.ingest	QUIC	Етап 1	Приймає FIFO-пакет до 100 точок (sessionId, driverId, brandId, points), повертає { "acceptedIds": [...] }.
coop.sync_peers	RUDP / QUIC	Етап 2	Приймає поточний стан EKF та observedPeers (10 Гц), повертає екстрапольовані координати підтверджених matchedDonors.
coop.request_moq_ingest	QUIC	Етап 3	Генерує JWT-токен та повертає параметри підключення до moq-relay (relayUrl, broadcastPath, authToken, maxGroupAgeMs).


5. Нефункціональні вимоги та критерії приймання

• Затримки (Latency):
• Обробка запиту coop.sync_peers у RedisCoopNavStorage — не більше 5 мс.
• Повний цикл обміну (RTT) по QUIC/RUDP у мережі 4G — до 60–80 мс.
• Час життя відеогрупи в MoQ (max_group_age_ms) — не більше 80 мс.
• Точність та автономність:
• В умовах повної відсутності GNSS за наявності хоча б 1 підтвердженого авто-донора в полі зору камери — похибка позиціювання не перевищує 3–5 метрів.
• У режимі OFFLOAD_CV завантаження CPU смартфона не повинно перевищувати стандартний відеозапис (відсутність тротлінгу протягом 1 години поїздки).
• Надійність та сумісність:
• Жодна точка трекінгу не втрачається при обриві зв'язку (збереження в зашифрованій FIFO-черзі з підтвердженням лише суворого префікса).
• Усі Rust-крейти проходять перевірку архітектурних меж python3 tools/check-architecture.py та матриці фіч tools/check-features.sh.
