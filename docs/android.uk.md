# Інтеграція з Android

Android source set містить foreground service, адаптери місцезнаходження й сенсорів,
зашифроване сховище сесії та FIFO-чергу. Бібліотека навмисно не має типового сервера чи
глобального singleton: host-застосунок надає автентифікований `TrackingTransport` і запускає
відстеження лише після підтвердження зміни користувачем.

## Налаштування host-застосунку та дозволи

Об'єднаний маніфест бібліотеки оголошує location foreground service і дозволи
`FINE`, `COARSE`, `BACKGROUND`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_LOCATION`,
`ACTIVITY_RECOGNITION`, `POST_NOTIFICATIONS`, `INTERNET` та `WAKE_LOCK`. Host-застосунок має
реалізувати `AndroidTrackerProvider` і вказати цей `Application` у `android:name`:

```kotlin
class FleetApplication : Application(), AndroidTrackerProvider {
    override fun createTrackingTransport(context: Context): TrackingTransport =
        RpcTrackingTransport(hostRpc) // Адаптер наявного з'єднання host-застосунку.
}
```

`hostRpc` реалізує `TrackingRpcTransport`; дивіться [CoopNav](coopnav.uk.md).
Типового endpoint у бібліотеці немає.
За потреби можна перевизначити `createTrackerLogger`, `createMapMatcher` і `trackerConfig`;
типовий logger записує діагностику в Android Logcat. Якщо host не надав provider, сервіс
повідомить про помилку ініціалізації та зупиниться.

Запускайте сервіс лише з видимої Activity після отримання дозволів і підтвердження/автентифікації
зміни. Не запускайте його з receiver, callback завантаження системи, worker, під час запуску
застосунку або фонового завдання. Android вимагає поетапних запитів runtime-дозволів:
спочатку дозвіл на місцезнаходження під час використання, а потім окремо — фонове
місцезнаходження, якщо цього вимагає ОС. Дозвіл сповіщень варто запитувати доречно;
розпізнавання активності необов'язкове, і відмова вимикає переходи, але не відстеження
місцезнаходження. `AndroidTracker.permissionsForHost()` повертає назви runtime-дозволів
для поточної версії ОС; це перелік, а не рекомендація просити фоновий і foreground-дозволи в
одному діалозі.

```kotlin
// Після успішного запиту дозволів і підтвердження зміни сервером:
val session = TrackingSession.fromConfirmedShift(sessionId, performerId, brandId)
AndroidTracker.startConfirmedShift(this, session)

// З кнопки у видимій Activity або через дію зупинки у сповіщенні:
AndroidTracker.stop(this)
```

Передавайте автентифікований `sessionId` і підтверджену host-застосунком особу. Помічник
перевіряє наявність потрібних дозволів і фокус вікна Activity. Починаючи з Android 10,
безперервне відстеження потребує фонового дозволу на місцезнаходження; новіші версії Android
додатково обмежують запуск foreground service та його тип location. Якщо ОС відхиляє запуск або
дозвіл відкликано, host має пояснити це користувачу та запропонувати явне відновлення.

Бібліотека створює постійне сповіщення з низьким пріоритетом, перекладене англійською та
українською. У маніфесті встановлено `allowBackup=false`, а також додано правила виключення даних
із резервних копій. Це налаштування стосується всього застосунку: якщо host перевизначає політику
резервного копіювання, переконайтеся, що черга та зашифрована сесія й надалі виключені. Файл
сесії зберігається в `noBackupFilesDir`.

## Спостереження за станом і зупинка

Запущений сервіс надає стан спільного bloc через локальний binder. Підключайтеся лише після
явного запуску; помічник навмисно не використовує `BIND_AUTO_CREATE`, тому спостереження за
станом не може запустити відстеження.

```kotlin
val connection = object : ServiceConnection {
    override fun onServiceConnected(name: ComponentName, binder: IBinder) {
        val state = (binder as TrackerForegroundService.TrackerBinder).state
        lifecycleScope.launch { state.collect { trackerState -> renderTrackingStatus(trackerState) } }
    }
    override fun onServiceDisconnected(name: ComponentName) = Unit
}

AndroidTracker.bind(this, connection)
// Від'єднайте цей connection під час знищення Activity, що спостерігає.
```

Перед надсиланням `Start` сервіс зберігає підтверджену сесію та повертає `START_STICKY` для
відстеження. Відновити цю зашифровану сесію може лише sticky-перезапуск з боку ОС. Явна зупинка
одразу блокує callback і скасовує збирання та надсилання даних. Сервіс повертає
`START_NOT_STICKY`, намагається видалити збережену сесію та зупиняється навіть у разі помилки
видалення. Помилку видно у стані binder і журналі; залишкові дані не запускають відстеження.
Щоб відновити відстеження після зупинки, host має підтвердити зміну. Примусова зупинка,
видалення застосунку, системна політика або втрата дозволів можуть завадити перезапуску.
При зміні ідентичності старий runtime зупиняється до очищення його сесії. Якщо очищення
або збереження нової сесії не вдається, відстеження залишається зупиненим, а сервіс
повідомляє про помилку.

Для спостереження рівня застосунку зберігайте binder поза Activity й викликайте його suspend-метод
`stopTracking()` після виходу або завершення сесії, зокрема у фоні. Він очікує завершення runtime.
Якщо binder недоступний, `AndroidTracker.stopFromHost(context)` очищає зашифровану сесію
та зупиняє наявний сервіс, не запускаючи нового.
Перевизначте `AndroidTrackerProvider.allowsStickyRestore(context)` зі значенням `false`,
якщо host вимагає нової перевірки авторизації/реєстрації після завершення процесу.
Звичайний фоновий збір продовжується, але sticky-перезапуск ОС не відновить збережену сесію host.

Під час активної сесії, зокрема у стані `STILL`, сервіс утримує частковий wake lock для CPU:
тайм-аут 60 секунд поновлюється кожні 30 секунд. Блокування знімається при зупинці та
невдалому запуску. Це збільшує витрати батареї та не обходить Doze чи обмеження виробника.

## Поведінка та обмеження платформи

- Runtime надсилає спільному bloc подію `Tick` раз на секунду. У русі запит місцезнаходження має
  інтервал 1 секунда, високу точність, нульове пакетування і чекає, доки провайдер вважатиме фікс
  точним. Активний лише один потік. Основний — fused. Платформний GPS запитується лише після
  відмови fused, зокрема без робочих Google Play services. Мережа запитується лише коли жоден
  точний провайдер не стартував, і `PlatformError` прямо каже, що мережеві фікси не є точним
  резервом. Пасивний провайдер не використовується.
  `LocationFix` зберігає час провайдера та Android `elapsedRealtimeNanos`; запізнілі callback не
  позначаються як нові.
- Поки активне вимірювання руху, запитується частота приблизно 50 Гц, зокрема до підтвердження зупинки.
  Rotation vector (або резервні сенсори
  сили тяжіння та магнітного поля) переводить прискорення в земну систему координат. Магнітна
  північ коригується схиленням `GeomagneticField`, а поздовжнє прискорення обчислюється як
  `east * sin(course) + north * cos(course)`. Обидва параметри надходять лише з прийнятої
  bloc оцінки GPS або fused, а не з необроблених вимірів. Поздовжнє прискорення використовує
  цей курс до 3 секунд від монотонної часової позначки прийнятої оцінки; старіший курс
  не передається, щоб поворот не проєктувався на попередній трек. Прогноз не поновлює
  цей строк. Вісь кріплення телефона не припускається. Yaw — це від'ємна складова вектора
  правобічного Android-гіроскопа вздовж світової осі вгору, відповідно до напряму за годинниковою
  стрілкою у спільному ядрі. Свіжа величина прискорення без складової тяжіння й доступні показники
  барометра надходять до ядра навіть за відсутності навігаційних даних. Поздовжнє прискорення та
  кутова швидкість окремо мають значення `null`, якщо для них бракує даних. Це дає ядру змогу
  виявити спокій ще до першої оцінки руху. Виміри для пробудження зі стану `STILL` містять
  величину прискорення, а обидва навігаційні параметри — `null`. Про відсутнє обладнання
  повідомляється через `PlatformError` і logger.
- У стані `STILL` точні сенсори та raw GNSS призупиняються. Місцезнаходження лишається
  точним сторожем з інтервалом 5 секунд, щоб справжній початок руху міг зняти якір зупинки.
  Зміна цього інтервалу не знімає колбек локації. Перший fused-результат не утримується
  до точного розв'язку; кешований фікс не старший за 5 секунд може бути відданий.
  Справжня втрата сигналу й далі очищає оцінку через 15 секунд, і позначка на мапі зникає. Якщо доступні,
  залишаються низькочастотний акселерометр і апаратний сенсор значного руху; три виміри
  прискорення понад 0,8 м/с² відновлюють точне сенсорне відстеження. Для пробудження від
  прискорення віднімається останній надійний вектор тяжіння, який уточнюється лише за залишкового
  прискорення менше 0,2 м/с². Підтримка пристроїв і частота вимірювань відрізняються.
- Переходи активності (спокій, ходьба, автомобіль) використовують mutable `PendingIntent` із
  явно визначеним приватним receiver, щоб Play services могли додати результати. Receiver
  підключається без `BIND_AUTO_CREATE` і передає дані лише відповідному активному runtime;
  він ніколи не запускає й не відновлює відстеження. Без Play services або дозволу цей
  допоміжний сигнал недоступний.
- Апаратний датчик кроків зберігає монотонну часову позначку виміру, тож запізнілі кроки
  не вважаються поточними. За наявності барометра свіжий тиск у гПа додається до активних
  вимірів руху; відсутні або застарілі значення не додаються.
- Raw GNSS необов'язковий. Значення AGC/CN0 додаються лише за наявності. Перетворення часу UTC
  виконується лише коли GNSS clock надає кількість високосних секунд і повний bias: враховуються
  GPS epoch і різниця GPS-UTC. Інакше `utcTimeMs` дорівнює `null` (час не перевірений). Raw GNSS
  недоступний на частині пристроїв.
- Спільне ядро ігнорує IMU-виміри віком понад одну секунду та завершує прогноз позиції після
  15-секундного горизонту; Android зберігає монотонні часові позначки для цих перевірок.
- `EncryptedTrackQueue` зберігає серіалізовані точки у SQLCipher з AES-GCM і
  `PRAGMA synchronous=FULL`. HMAC-ключ Android
  Keystore створює непрозорий partition зі складених із довжиною полів ідентифікаторів; AAD
  кожного шифротексту прив'язує його до partition і ID точки. Один mutex серіалізує append,
  peek, size та підтвердження точного префікса для кожного екземпляра черги; підтвердження
  транзакційне. Помилки автентифікації, схеми чи пошкодження SQLite повідомляються без
  автоматичного видалення або повторного створення бази. Втрата ключа Keystore може зробити
  зашифровані дані   недоступними. Якщо в черзі є записи, бібліотека повідомляє про відсутність ключа
  ідентичності, а не створює новий ключ, який приховав би старі розділи.
  Ключ бази SQLCipher окремо захищений Keystore; старі рядки мігрують транзакційно
  без видалення вихідної бази. Дивіться [сховище](storage.uk.md).
- Обидва сховища записують IV, створений Android Keystore для кожного шифрування AES-GCM.
  `EncryptedSessionStore` використовує `AtomicFile`. `SecurePointIdGenerator` створює
  криптографічно випадкові 128-бітні ID. `AndroidTrafficCounter` вимірює байти UID від моменту
  створення конкретного лічильника й кидає помилку, якщо Android не підтримує цю статистику.

Сповіщення Android — єдиний UI бібліотеки. Його видимі рядки визначені в
`values/strings.xml` та `values-uk/strings.xml`; пояснення дозволів, підтвердження зміни,
повторні спроби та інтерфейс помилок належать host-застосунку.
